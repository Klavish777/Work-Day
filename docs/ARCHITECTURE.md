# Архитектура

Проект построен вокруг одного принципа: **денежные решения должны быть проверяемы
по отдельности**. Поэтому вместо одного большого торгового скрипта здесь модули,
каждый из которых можно протестировать без терминала, без интернета и без Windows.

## Слои

```
                │  agent.py — оркестратор: порядок шагов цикла         │

                        │
   ┌────────────────────┼─────────────────────┬───────────────────────┐

```

## Почему именно так

### `broker.py` — единственное место с `MetaTrader5`

Пакет `MetaTrader5` существует только под Windows, поэтому импорт делается **лениво**
внутри функции. Всё остальное (риск, фичи, модель, бэктест, тесты) работает на любой
платформе. Побочный эффект: CI/разработка не требуют ни Windows, ни терминала.

Брокер не «додумывает» параметры инструмента: `digits`, `point`, `tick_value_loss`,
`volume_step` берутся из терминала. Ошибка здесь исказила бы размер риска на каждой
сделке.

### `sizing.py` + `specs.py` — деньги считаются из риска

```
loss на 1.0 лот = (SL в цене / point) × value_per_point_per_lot
объём           = equity × risk% / loss на 1.0 лот
```

Затем объём **округляется вниз** к шагу лота, проверяется на минимальный/максимальный
объём и на ограничение по марже. Если минимальный лот рискует больше лимита — сделка
**отклоняется**. Самая частая ошибка самодельных ботов — «округлим вверх до 0.01»;
здесь это невозможно.

`specs.py` держит `SymbolSpec` — «зеркало» `symbol_info`. Благодаря этому формула
одинакова в live и в бэктесте, а тесты не требуют терминала.

### `risk.py` + `state.py` — лимиты, которые нельзя забыть

Все проверки собраны в одном методе `RiskManager.check_entry`, который возвращает
решение со списком причин. Порядок проверок фиксирован, и в журнал пишется полный
список — при разборе видно, что именно заблокировало вход.

Состояние (дневная/недельная статистика, пик equity, halt, открытые тикеты) хранится
в `state/agent_state.json`. Это важнее, чем кажется: без этого перезапуск агента
обнулял бы лимиты и дневной стоп становился бы фикцией.

### `features.py` + `model.py` — «предсказываем не цену»

Цель обучения: `1`, если движение вперёд превышает издержки (спред + комиссия) плюс
небольшой запас в ATR. Модель отвечает на вопрос «стоит ли вообще платить комиссию
за эту сделку», а не «какая будет цена».

Валидация — только `walk-forward`: обучение и проверка идут по времени, между ними
«забор» (embargo) величиной с горизонт. Масштабирование и импьютация живут **внутри
sklearn Pipeline**, чтобы обучаться на train-части каждого фолда, а не на всей истории.

Признаки строятся строго из прошлого. Это проверяется тестом `test_no_lookahead_in_features`:
признаки на одних и тех же барах совпадают, если обрезать будущее.

### `signals.py` — сигнал ≠ ордер

Пайплайн: фильтры (сессия, спред, минимальная волатильность) → модель → порог →
новостной фильтр → расчёт стопов от ATR. Всё, что не прошло, возвращает `side="none"`
с **человекочитаемой причиной** — это то, что показывается в `status` и в отчёте цикла.

### `sentiment.py` — LLM как предохранитель, не как оракул

Два уровня: детерминированная эвристика по событиям/терминам (работает всегда) и
опциональная локальная LLM с OpenAI-совместимым API, которая возвращает строгий JSON
`{risk, block, reason}`. Ответ валидируется, при любой ошибке — откат к эвристике.
LLM не может создать сигнал: только запретить вход.

### `execution.py` — единственный путь к ордерам

Строит заявку (цены SL/TP от реального ask/bid с округлением до `digits` и проверкой
минимальной дистанции брокера), отправляет, проверяет проскальзывание, ведёт позиции
(безубыток при `breakeven_at_r`, опциональный трейлинг по ATR) и считает результат
закрытых сделок из истории.

### `agent.py` — оркестратор без «умных» решений

```
1. подключение + снимок счёта
2. прокатка периодов (день/неделя) + обновление пика equity
3. kill switch → аварийное закрытие своих позиций и halt
4. синхронизация закрытых сделок → дневная/недельная статистика
5. ведение позиций (безубыток, трейлинг, закрытие позиций без стопа)
6. по каждому символу: данные → сигнал → риск → размер → заявка
7. heartbeat, dashboard.json, отчёт цикла, уведомления
```

Шаг 4 — тот, который чаще всего забывают в самодельных ботах: без него лимиты не
учитывают реальный результат и дневной стоп никогда не срабатывает.

Вся математика выведена в отдельные модули; оркестратор отвечает только за порядок
и за то, чтобы ни один шаг не выполнялся «через раз».

### `virtual_broker.py` + `tools/demo_cycle.py` — проверка самого агента

Бэктест отвечает на вопрос «работает ли идея», а виртуальный брокер — «работает ли
программа»: состояние, лимиты, безубыток, учёт закрытых сделок, дашборд. Он
реализует тот же интерфейс, что `MT5Broker` (duck typing), поэтому агент не знает,
торгует он на синтетике или через терминал. Демо-прогон изолирован в `state/demo/`,
чтобы виртуальные сделки не влияли на реальные лимиты.

### `backtest.py` — проверка идеи до денег

Три отличия от «наивных» бэктестов: издержки (спред + комиссия + проскальзывание)
вычитаются из каждого трейда; если бар закрыл и стоп, и тейк — считается **стоп**;
по умолчанию симуляция идёт по out-of-sample части. На выходе — явный вердикт
`GO / NO-GO` по порогам из конфига.

## Режимы работы

| Режим | Ордера | Счёт | Для чего |
|---|---|---|---|
| `shadow` | нет (только расчёты) | любой | посмотреть, как агент думает |
| `paper` | да | **только демо** | собрать статистику 1–3 месяца |
| `live` | да | реальный (или демо) | после трёх барьеров безопасности |

## Как расширять

**Новый инструмент.** Добавь блок в `trading.symbols` с уникальным `magic` →
`fetch --symbol NEW --save-specs` → `train --symbol NEW` → `backtest --symbol NEW`.
Модель для каждого символа хранится отдельно (`models/signal_NEW_M15.joblib`).

**Новые признаки.** Добавь колонку в `build_features` и не забудь про правило
«только прошлое». Тест `test_no_lookahead_in_features` поймает ошибку.

**Другая модель.** В `model.py::make_estimator` добавь вариант (например,
`HistGradientBoostingClassifier`, который умеет NaN) и впиши имя в
`signal.model`. Ничего больше менять не нужно: обучение, отчёт и применение
работают через один интерфейс `predict_proba_up`.

**Свой источник новостей.** Реализуй функцию, возвращающую список заголовков, и
подключи её в `SentimentFilter.collect_headlines`. Дашборд и события в JSONL уже
покажут результат фильтра.

## Границы и осознанные упрощения

* Один процесс на один счёт. Мультисчётность в проекте намеренно не поддерживается:
  это увеличивает риск ошибок и не нужно для заявленной задачи.
* Бэктест симулирует по барам (не по тикам) — поэтому в отчёт всегда встроено
  предупреждение о переоценке результата.
* Агент не торгует частичными объёмами и не строит лестницы заявок — сознательное
  упрощение учёта.
* Свопы и дивиденды в бэктесте не моделируются: влияние на коротких сделках мало,
  но об этом нужно помнить при удержании позиций через ночь.
